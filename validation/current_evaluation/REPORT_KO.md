# 현재 KnitCode 분석 엔진 평가

이 문서는 **개선 전 평가**를 보존한다. 개선 후 비교는
[`IMPROVEMENTS_KO.md`](IMPROVEMENTS_KO.md)를 참고한다.
개선 전 원시 결과는 `before_improvements.json`, 현재 엔진의 재실행 결과는 `probes.json`이다.

평가일: 2026-10-21. 실행 환경: Python 3.12.2 / macOS.
대상: 현재 체크아웃의 `ast_parser → symbol_builder → graph_builder/object_flow → call_status`.
분석 엔진은 변경하지 않았다. VSIX의 UI 실행은 이번 평가 범위가 아니다.

## 판단

현재 엔진은 함수 관계를 탐색하는 보조 도구로 유용하다. 완전한 Python 의미 분석이나
정확한 변경 영향 판정의 단독 근거로 쓰기에는 미지원 패턴과 잘못된 연결이 있다.
학습 모델이 아니라 Python 표준 `ast`와 직접 구현한 심볼·추상 값 흐름 분석이다.
문법 파싱 성공과 올바른 호출 대상 추론은 구분해야 한다.

## 이번에 직접 실행한 결과

- 기존 자동 테스트: **267개 통과**. 지원 기능의 회귀 검증이며 실전 정확도 수치는 아니다.
- 별도로 작성한 집중 사례: **22개 중 대상 집합 정확 일치 9개**.
- 22개 모두 문법 파싱 오류 없음. 불일치는 주로 호출 해석 단계에서 발생했다.
- 기본 호출·분기·팩토리·콜백·객체 별칭에 의한 필드 갱신: **5/5**.
- None 재할당·타입 불명 매개변수·await하지 않은 coroutine에 대한 연결 유보: **3/3**.
- 튜플 언패킹: 통과.
- 리스트/딕셔너리 인덱싱, 리터럴 getattr, property 반환, await 반환,
  with 바인딩, match 대입, 클로저 반환: **8개에서 대상 누락**.
- 반복문 2회 실행, finally의 return 덮어쓰기, 상수 False 분기:
  **3개에서 실제 가능한 대상보다 넓은 후보 집합**.
- 데코레이터에 의한 함수 교체, 클래스 메서드 재할당:
  **2개에서 실제 교체된 대상 대신 기존 정의로 연결**. 둘 다 `SOURCE_BACKED`로 표시됐다.

| 영역 | 사례 수 | 대상 집합 일치 |
|---|---:|---:|
| 기본 기능 | 5 | 5 |
| 연결 유보 | 3 | 3 |
| 경계 기능 | 9 | 1 |
| 제어 흐름 | 3 | 0 |
| 동적 바인딩 | 2 | 0 |

이 표본은 약점을 드러내도록 의도적으로 선택했으며, 무작위 실제 코드 표본이 아니다.
대상은 수작업으로 정했고 각 사례의 focus 호출 한 곳만 평가한다.
타입 불명 매개변수 사례는 런타임 정답 대신 연결 유보 정책을 검사한다.
따라서 9/22를 전체 Python 정확도로 일반화할 수 없다.
focus 타깃 간선 기준 TP=10, FP=5, FN=11, Precision=66.7%, Recall=47.6%지만
이 역시 이 합성 표본에만 해당한다. `MAY_CALL`의 과대 근사는 의도된 절충일 수 있으며
곧바로 구현 결함과 동일하게 해석하면 안 된다.

## 구체적 오연결 사례

```python
def replace(fn): return B().run
@replace
def original(): pass
def go(): original()
```

실제 바인딩은 `B.run`이지만 엔진은 `original`로 연결한다.

```python
def replacement(self): pass
def go():
    A.run = replacement
    obj = A()
    obj.run()
```

실제 대상은 `replacement`지만 엔진은 `A.run`으로 연결한다.
이 사례들은 단순한 UNKNOWN 누락보다 우선적으로 다뤄야 한다.
소스에 정의가 존재한다는 `SOURCE_BACKED`는 런타임 대상의 정확함을 보장하지 않는다.

## 파싱과 성능

UTF-8 파일은 정상 처리했고 잘못된 문법은 SyntaxError로 보고했다.
유효한 `# coding: latin-1` 파일은 UTF-8 강제 읽기로 누락했다.
호스트 Python의 `ast`를 사용하므로 지원 문법도 실행 인터프리터의 영향을 받는다.

합성 독립 모듈의 분석 파이프라인을 3회씩 실행한 중앙값:

| 파일 | 줄 | 명시적 호출 | 시간 |
|---|---:|---:|---:|
| 50 | 250 | 100 | 약 0.011초 |
| 200 | 1,000 | 400 | 약 0.048초 |

두 규모 모두 흐름 분석 cutoff는 0이었다. 작은 단순 코드의 비용만 측정했다.
Git 이력, JSON/HTML 저장, VS Code 렌더링 및 대형 프로젝트의 상호 호출은 포함하지 않는다.
메모리·대형 프로젝트 확장성은 이번 측정으로 판단할 수 없다.

## 기존 평가 자료 해석

저장된 `validation/object_flow/measurement_after.json`의 22사례 결과에는
Precision 100%, Recall 91.7%가 기록돼 있다. 이번 경계 사례 22개와는 별도의 표본이다.
해당 기록은 다른 환경의 과거 실행이며, 원래 gold 사례 디렉터리가 현재 저장소에 없어
같은 입력으로 재실행하지 못했다. 현재 엔진의 전체 정확도 근거로 인용하면 안 된다.
실제 저장소에서 해결 호출 수가 증가했다는 기존 자료 역시 수작업 정답과 대조하지 않으면
정확도 향상의 증거가 되지 않는다.

## 개선 우선순위

1. 교체된 데코레이터 바인딩·클래스 속성 재할당을 추적하거나, 불명확하면 UNKNOWN으로 낮춘다.
2. UTF-8 강제 읽기를 Python 인코딩 선언을 존중하는 방식으로 개선한다.
3. await, 리터럴 인덱싱, match, property, 클로저를 대표 사용 빈도에 따라 확장한다.
4. finally 반환 우선순위를 수정하고 반복문 고정점·경로 조건 추적을 별도 설계한다.
5. 실제 사용 대상 저장소에서 내부 호출 정답 표본을 독립 검토하고, caller·callsite·target
   세 축으로 Precision/Recall을 측정한다. 기능별로 나누고 튜닝에 쓰지 않은 표본을 남긴다.

재현: 저장소 루트에서 `python3 -B scripts/evaluate_engine.py`.
전체 입력 소스·기대 대상·관측 대상·certainty·측정 시간은 옆의 `probes.json`에 있다.
